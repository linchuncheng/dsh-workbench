# 先查库，再动手

造轮子不是错，错在没算过账。每一处通用能力先问：有没有成熟稳定、许可合适、体量可接受的库？
有就先用；没有、或代价更高，才自研，并把账记下来。

**先查库**是这条技能的 leading word：写任何通用工具前，先说一次「先查库」。

## 什么时候用

- 新增或重写一个通用能力：解析、校验、序列化、glob、原子写、文件锁、重试、退避、semver、URL、Markdown、CSS、日志、CLI 参数、表格、日期、HTTP、浏览器驱动。
- 审 diff 时看到一段手写解析、手写协议，或第二份同样的工具。
- 有人问「为什么这里不用 xx 库」。

业务规则本身（版本排序、权限、领域状态机）不算通用能力；它们留在业务层，库只替掉外围的格式与机制。

## 四步

1. **划边界**：列出这段代码里哪些是通用机制（格式、传输、锁、重试），哪些是业务规则。只给通用机制找库；业务规则不进库。
2. **列候选**：至少两个，查最近发布、issue 响应、license、Node / 浏览器兼容、打包后体积、传递依赖、安全记录、API 贴合度。已在 `pnpm-lock.yaml` 里的优先。
3. **试一次**：用真实夹具跑通，量 bundle / 启动 / 内存；读它的错误语义，确认能保留现有文案与返回形状。
4. **记账**：采用就写下版本与替换点；自研就写下「不选库」的理由与退路。把这段放进 commit message、spec 或 ADR，随改动一起提交。

## 常见映射

| 手写的东西 | 先看 |
| --- | --- |
| YAML 读写 | `yaml`（`parse` / `parseDocument` + `LineCounter`） |
| workspace glob、目录发现 | `tinyglobby` |
| CSS 规则 / 声明扫描 | `postcss` |
| Markdown 标题锚点 | `markdown-it` + `github-slugger` |
| 原子写 | `write-file-atomic` |
| 浏览器下载 / 版本解析 | `@puppeteer/browsers` |

## 自研的正当理由

- 库比需求大一个数量级，或会把浏览器 / 宿主 bundle 撑大。
- 行为与文案必须逐字保留，库的消息 / 返回形状改不动。
- 库无人维护、license 不合、有 native binding / 平台限制、安全记录差。
- 只差 5～20 行，且没有第二处会复用。
- 库的抽象会漏掉关键领域规则，用了反而要包一层再拆。

「没查」不是理由；「查过，因为 X 不用」才是。

## 记账格式

```md
能力：<一句话>
候选：<lib@ver>（license / 最近发布 / 打包体积）、<lib2@ver> …
结论：采用 <lib@ver> / 自研
理由：<体积、行为、维护、平台、文案…>
退路：<什么时候重评；换掉时改哪里>
```

实际落点是 `scripts/arch/library-decisions.mjs`：`check:deps` 会校验每条记录的字段，以及 `adopt` 是否登记在
`scripts/arch/stack.mjs` 的 `STACK_CAPABILITIES` 里；`defer` 不能同时出现在那张表。

## 完成判据

- diff 里每一处新写的通用机制，都能指到一个库，或指到一条「不选库」的记录。
- 同一能力只有一处实现；第二处出现时先合并，再谈库。
- 记录跟着代码走：commit / spec / ADR 至少一处，不散落在聊天里。
